# task-invalidation Specification

> **Change**: `extraction-versioning-schema`

## ADDED Requirements

### Requirement: The Mark Is a Row in `task_invalidations`

A task invalidation mark MUST be stored as a row in a dedicated `task_invalidations` table carrying
`task_id`, `reason`, `marked_by`, `marked_at`, `revoked_by` and `revoked_at`. The mark MUST NOT be
stored as columns on `tasks`, because the record of who revoked and when is required and only a
row per mark event can hold it.

#### Scenario: A mark persists its full record

- **GIVEN** a task generated by a completed extraction and a user who judges it invalid
- **WHEN** a mark is stored with a reason
- **THEN** a `task_invalidations` row exists with that `task_id`, the `reason`, the marking user in
  `marked_by`, and the marking timestamp in `marked_at`
- **AND** `revoked_by` and `revoked_at` are null

#### Scenario: The mark is not a column pair on the task

- **GIVEN** migration `0028` has been applied
- **WHEN** the `tasks` schema is inspected
- **THEN** no invalidation or invalid-reason columns exist on `tasks`
- **AND** the only home of a mark is the `task_invalidations` table

### Requirement: The Reason Is Mandatory as a Database Invariant

A mark without a reason MUST NOT be persisted. The ban on an empty reason MUST be enforced by a
database CHECK on the trimmed `reason` value, not only by application or UI validation.

#### Scenario: Empty reason is rejected by the database

- **GIVEN** the `task_invalidations` table
- **WHEN** an insert attempts a mark whose `reason` is empty or whitespace only
- **THEN** the database rejects the insert through the CHECK constraint on the trimmed reason
- **AND** no mark row exists for that attempt

#### Scenario: A bounded non-empty reason is accepted

- **GIVEN** the `task_invalidations` table
- **WHEN** an insert stores a mark whose `reason` is non-empty text within the column's length bound
- **THEN** the row is persisted with that reason verbatim

### Requirement: At Most One Active Mark Per Task

At any moment, a task MUST hold at most one active mark — a mark whose `revoked_at` is null. This
MUST be enforced by a partial unique index on `task_id` where `revoked_at IS NULL`.

#### Scenario: Second active mark is rejected

- **GIVEN** a task with an active mark (its `revoked_at` is null)
- **WHEN** an insert attempts another mark for the same task without revoking the first
- **THEN** the database rejects the insert through the partial unique index
- **AND** the task still holds exactly one active mark

#### Scenario: A revoked mark does not block a new one

- **GIVEN** a task whose only mark is revoked (`revoked_at` is not null)
- **WHEN** a new mark is stored for that task
- **THEN** the insert succeeds
- **AND** the task again holds exactly one active mark

### Requirement: Revoking Is an Update, Never a Delete

Revoking a mark MUST update the existing row, recording who revoked it and when in `revoked_by` and
`revoked_at`. The row MUST never be deleted. Re-marking after a revoke MUST create a new row, so
that both events remain readable.

#### Scenario: Revoke records who and when on the same row

- **GIVEN** a task with an active mark
- **WHEN** the mark is revoked
- **THEN** the same row now carries the revoking user in `revoked_by` and the revocation timestamp
  in `revoked_at`
- **AND** the original `reason`, `marked_by` and `marked_at` are unchanged

#### Scenario: A revoked mark is never deleted

- **GIVEN** a revoked mark row
- **WHEN** any product operation runs against the task or its story
- **THEN** the revoked row still exists in `task_invalidations`

#### Scenario: Re-mark after revoke keeps both events readable

- **GIVEN** a task whose mark was revoked
- **WHEN** the task is marked invalid again
- **THEN** a second `task_invalidations` row exists with its own `reason`, `marked_by` and
  `marked_at`
- **AND** the first row still records the first marking and its revocation

### Requirement: Actor References Survive Account Deletion

`marked_by` and `revoked_by` MUST reference users with `ON DELETE SET NULL`, matching the
repository's `projects.created_by` attribution convention. When an account is deleted, the actor
reference alone MUST be nulled; the `reason`, `marked_at` and `revoked_at` of the mark MUST never
disappear with the user.

#### Scenario: Deleting the marking user nulls only the reference

- **GIVEN** a mark row whose `marked_by` references a user account
- **WHEN** that user account is deleted
- **THEN** the mark row still exists with the same `reason` and `marked_at`
- **AND** `marked_by` is null
- **AND** no other field of the mark was changed

#### Scenario: Deleting the revoking user preserves the revoke record

- **GIVEN** a revoked mark row whose `revoked_by` references a user account
- **WHEN** that user account is deleted
- **THEN** `revoked_at` still holds the revocation timestamp
- **AND** `revoked_by` is null

### Requirement: The Mark Belongs to the Version It Was Made On

An invalidation mark MUST reference exactly one task through `task_id`, and through that task the
one extraction version that produced it. The mark's version membership is a fact of storage via the
task reference; the mark MUST NOT carry its own version column and MUST NOT be duplicated onto
equivalent tasks.

#### Scenario: The mark resolves to one version through its task

- **GIVEN** a task that belongs to extraction v2 of its story, with an active mark
- **WHEN** the mark's version is resolved through the task's `extraction_id`
- **THEN** it resolves to v2 and only to v2

#### Scenario: A mark is not duplicated across versions

- **GIVEN** a task marked invalid in v1
- **WHEN** a new extraction produces v2 with a task of the same title
- **THEN** no mark row exists for the v2 task
- **AND** the stored mark still points only at the v1 task
